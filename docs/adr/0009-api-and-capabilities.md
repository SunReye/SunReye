# 9. API and capabilities

Status: accepted (2026-11-08), amended (2026-11-09)

## Context

The SPA, the CLI and integrations consume one surface. v4 retrofitted capability gating onto routes the core did not serve yet.

## Decision

**Shape.** REST with JSON under `/api/v1`, described by one OpenAPI document generated from the Rust types and served at `/openapi.json`. Each route registers together with its description (`utoipa-axum`). The SPA client and its TypeScript types are generated from it. `v1` changes only additively; a break is `v2` beside `v1`. API version, core version and profile schema are three separate numbers.

**Capabilities.** `GET /api/v1/capabilities` returns the core version, the schema range, transports, bindings, step kinds, enabled features and per-device capabilities derived from roles. Under `devices`, keyed by device id, each lists its `estimated` series: those computed from others, not measured, such as a parallel string's `pv.string.power` in the layout in force (ADR 17). It comes from the same table the WASM exposes. Each also lists its `settings` from its profile, in the profile's order: key, `range` or `values`, `step` and `enable` (ADR 8), with the device's `writes` switch (ADR 7), so the SPA renders setting controls without naming a profile. The SPA renders from it and never branches on a brand or profile name.

**Configuration.** Admin only. `/api/v1/connections` and `/api/v1/devices` are added with `POST`, listed with `GET`, changed with `PUT /{id}` and removed with `DELETE /{id}`; a connection in use is not removed. A connection reads back the names of its secrets, never their values; in a write, a secret with a value is set, one with `null` removed and an absent one kept. `POST /api/v1/scan` runs the setup scan (ADR 6) over an optional `subnet` and returns each endpoint found with the devices proposed behind it. `PUT /api/v1/location` sets the plant's location (ADR 17). `GET` and `PUT /api/v1/timezone` read and set the plant timezone (ADR 3) by IANA name; the host's zone stands in until it is set, and a change applies from the instant it is made. `GET` and `PUT /api/v1/spot-prices` read and choose the bidding zone spot prices are fetched for, `null` for none (ADR 12). `GET /api/v1/topology` reads the topology in force at `at`, or now, flagging each contested point, and `PUT` changes it from `appliesFrom` on (ADR 14): points in order, the root first, each naming its parent by its index among them and its claims as device and power role; a kept point names its id, a new one gets a fresh id. `GET /api/v1/changes` reads the change log (ADR 19).

**Settings.** `PUT /api/v1/devices/{id}/settings/{key}` returns the outcome and the failing step (ADR 7).

**Transport.** Plain HTTP. TLS is a documented reverse-proxy job.

**Auth.** The first run sets the admin password; there is no registration. Passwords use bcrypt at cost 12, as v4 did. A password longer than bcrypt's 72-byte limit is refused, never silently truncated. The SPA uses a cookie session: `HttpOnly`, `SameSite=Strict`, `Secure` when the request arrived over TLS (the proxy's `X-Forwarded-Proto: https`), expiring 30 days after its last use. Sessions live in memory, at most 64: a restart signs everyone out, and using a session writes nothing to flash. Failed logins back off exponentially per client address: 1 s after the first failure, doubling to 15 min, answered `429` with `Retry-After`; an attempt counts as failed until it succeeds, so concurrent guesses wait too. Integrations use bearer tokens scoped `read` or `admin`, sent as `Authorization: Bearer`. The admin creates them under `/api/v1/tokens` (`GET`, `POST`, `DELETE /{id}`), each with a name and a scope. A token is 256 random bits, shown once in the response that creates it; the core keeps only its SHA-256, which suffices at that entropy where bcrypt would cost every request, and holds the hashes in memory so a request reads no SQLite. A removed token is refused at once. The admin creates viewer accounts, each with a name and password, under `/api/v1/viewers` (`GET`, `POST`, `DELETE /{id}`); a viewer's name is unique, and removing a viewer ends its sessions. A viewer signs in at `/api/v1/login` with its `name` beside the password; the admin sends the password alone. Viewers share the admin's backoff. A viewer or `read` token reads live values and history. Configuration, the state of secrets, the write log and every write need admin; a signed-in caller without it is refused `403` `auth.forbidden`. Every route is classified public, read or admin in one table that the auth guard reads; an unclassified route needs admin, and a test fails for any route of the OpenAPI document missing from it. Read covers the session check, live values, problems, capabilities, history, the energy balance, forecasts, and the layout and module types the scene draws (ADR 20); `setup` and `login` are public; everything else is admin. Under Home Assistant ingress the core trusts HA's login: a request from the Supervisor's ingress address (`172.30.32.2`) that carries the ingress header `X-Ingress-Path` acts as admin, even before the first run sets a password. This trust is switched on only in the add-on image, through `--ingress` (ADR 2); any other source on the same port, or the Supervisor without the header, still needs the core's login.

**Live.** SSE at `/api/v1/live`: a full `snapshot` event on connect, then `delta` events only, no replay; a client that falls behind is disconnected and reconnects to a snapshot. One JSON object per tick, serialised once and shared by all clients. A tick is a 1 s window that coalesces every reading changed in it, whatever the poll cadences; a tick with no change sends nothing. Live reads memory, never SQLite.

**History.** `GET /api/v1/devices/{id}/history` by `series` (ADR 3, such as `pv.mppt.power[2]`) and the range `from` to before `to`, RFC 3339 instants. The server picks the tier so a series has at most 1,500 points (about one per pixel of a wide chart), returns time-weighted means and names the tier. A range of up to a day returns `raw` intervals while it holds at most 1,500 of them, else `bucket`: means over UTC-aligned buckets computed on read from change points, with their `width` in seconds, 60 s (a day is at most 1,441 of them); nothing is stored for buckets. Longer ranges return `hour` rollups up to 1,499 hours, the hour in progress read from change points, else `day` rollups up to 1,498 days of 23 hours. Each point is an interval, bucket or rollup with its own start and end, so the first may begin before `from`; a gap is not part of a mean, and a point has at least some value. History ends at the core's clock: the last value is not held into the future. A longer or empty range is refused as `history.range`. A counter's `raw` and `bucket` points are its readings and their time-weighted mean; past them it is refused as `history.counter`, as its rollups hold a delta, not a mean.

**Energy balance.** `GET /api/v1/balance` by the range `from` to before `to` returns each plant-local day starting in it with rolled-up history: its residual in kWh and each consuming point's (ADR 14). An empty range, or one longer than the day tier's, is refused as `history.range`.

**Forecasts.** `GET /api/v1/devices/{id}/forecasts` by series and range, with the same 1,500-point cap. It returns the latest issue by default; `issuedBefore` selects an earlier one, so forecast accuracy can be compared (ADR 15).

**Problems.** `GET /api/v1/problems` lists the conditions degrading the core by stable code, such as `clock.unsynced` (ADR 3).

**Errors.** `application/problem+json` (RFC 9457) with a stable machine `code`, such as `write.range` or `device.unreachable`, and no localised text. A device fault and a caller mistake have different codes and status classes. Error and problem codes are one closed set, listed as the `Code` enum of the OpenAPI document, so the SPA's text for each is checked against it (ADR 11).

## Considered options

- **GraphQL.** Rejected: one fixed client, and a generated REST client is cheaper.
- **WebSocket for live.** Rejected as the default: SSE is one-way, simpler and lighter; settings go through POST and PUT.
- **Client polling.** Rejected: it multiplies load for every viewer.

## Consequences

The OpenAPI document is a contract tested in the gate: every API test request checks that the route it reached is in the served document, so a route absent from it fails. The served document is committed at `crates/core/openapi.json` and the SPA's types are generated from that file; the gate fails when either is stale, and `bun run --cwd apps/web api` regenerates both.
