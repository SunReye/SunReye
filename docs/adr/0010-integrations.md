# 10. Integrations

Status: accepted (2026-11-08), amended (2026-11-09)

## Context

EVCC, MQTT devices and Home Assistant are neighbours, not special cases. The EVCC contract was verified in v4 against EVCC's source and a live instance: state topics are retained, keys are camelCase, loadpoints are 1-based, writes go to `<root>/loadpoints/<n>/<key>/set`, and `batteryBoost` errors unless the mode is `pv` or `minpv`, and a mode change clears it.

## Decision

- **EVCC is an official profile** with an `mqtt` binding. Its topics map to `ev` roles: `chargePower`, `vehicleSoc`, `sessionEnergy` (Wh, stored in kWh), `connected`, `charging`, `limitSoc`, `batteryBoost` and `mode`, whose text payloads (`off`, `now`, `minpv`, `pv`) read as 0 to 3 through an `enum` (ADR 5). `vehicleTitle` reads through an `enum` built from the car catalogue as the matching entry's id, `ev.vehicle.model` (ADR 20); another title is no value. A loadpoint is a device whose device address is its loadpoint index, from 1. Mode, limit SOC and battery boost are recipes with `mqtt` publish steps: mode first, boost last, a `precondition` on mode. Read-back is the retained state EVCC republishes within about 2 s; a write waits up to 5 s for it, and one EVCC does not republish is a `mismatch`. These writes run through the funnel of ADR 7 as admin actions, with the same audit and outcomes.
- **One MQTT client per broker connection,** owned by a task, with reconnect backoff from 1 s up to 60 s and an observed status (`connected`, `lastError`, `lastConnectedAt`) that the connection list reports. EVCC, custom MQTT profiles and the publisher share it. A broker is a connection of transport `mqtt`; its credentials are the secrets `username` and `password`, and its `topicRoot`, such as `evcc`, is required: a path without wildcards or a leading or trailing `/`, under which its profiles' topics sit. Another transport takes none. Its client id is random per start, so two installs on one broker never evict each other. A device behind a broker needs a profile with an `mqtt` binding, and such a profile needs a broker (`device.transport`); a device address is taken once per broker and topic root. The client subscribes to its devices' topics on every connect, so it receives their retained state again, and is replaced when its devices change. A broker sends a retained topic only on change, so its devices' values are republished every poll cadence while it is connected: a silent broker reads as held, a lost one as a gap (ADR 3).
- **One task per HTTP host connection,** of transport `http`: plain HTTP on the LAN, as Shelly and Fronius serve it; TLS waits for a vendor that needs it. It takes no `topicRoot` or `publish`. Its secrets `username` and `password` answer the host's Digest challenge (ADR 5); without them a challenged GET fails. A device behind it needs a profile with an `http` binding, and such a profile needs an HTTP host (`device.transport`). Every cadence (ADR 6) the task asks every GET of every device at once, each on Tokio's blocking pool through `ureq` (ADR 2) with the endpoint timeout, and publishes each device whose GETs all answered; a cycle with a failed GET backs off as an endpoint task does. It is replaced when its connection or devices change.
- **Outbound is read-only.** `GET /api/v1/roles/{role}` gives a scalar or indexed value for EVCC's HTTP custom meter, from the `plant` device (ADR 14) or from one device with `?device=`. Its body is the bare JSON number, in EVCC's sign convention: a battery is positive when discharging. A series with no live value is `role.none`; the endpoint takes a scoped `read` token. A broker connection with `publish` runs the MQTT publisher on its client, under its topic root: the `plant` device's role values on `<root>/plant/<series>`, coalesced over a second, in Home Assistant's sign convention (a battery is positive when discharging), and each device's availability, `online` or `offline` past the gap threshold, on `<root>/devices/<id>/availability`, sent on change and every cadence. It runs in the core with `read` scope: it publishes only live values, never configuration or another device's values, and offers no command topic. With `publish.discovery`, Home Assistant device discovery goes to `homeassistant/device/sunreye_<root>/config`, unretained, on every connect and on Home Assistant's birth message (`online` on `homeassistant/status`): one device, the plant, with a sensor per power role, state of charge and capacity, and a connectivity sensor per device, each expiring past the gap threshold so a stopped core reads as unavailable. Battery dispatch from EVCC is not offered (ADR 1, 7).
- **Conventions at the edge.** Roles carry one sign convention (ADR 4). Each adapter converts at its own edge and has a golden test against the consumer's documented convention.
- **Custom profiles** are community profiles with `mqtt` or `http` bindings, built with the CLI and distributed through a custom index (ADR 8). No scripting.
- **Settings.** A connection holds host, port, topic root, credentials and, for a broker, whether it publishes and with discovery; each loadpoint device holds its index. Both are entered in the SPA. Credentials are secrets (ADR 7). A connection is enabled by a flag; there is no separate integrations page and no mapping UI.

## Considered options

- **EVCC as code in the core.** Rejected: it would be the first non-Modbus special case and the format would never be tested against MQTT.
- **EVCC over REST.** Rejected: cookie authentication; MQTT state is retained and instant.
- **Accepting EVCC's battery dispatch.** Rejected: a control loop.
- **Retained discovery and values.** Rejected: a disabled publisher or a removed device would leave its entities in Home Assistant until cleared by hand; the birth message and `expire_after` cover a restart of either side.

## Consequences

EVCC needs `mqtt` publish steps and `precondition` in the format on day one, which also covers the Shelly and Victron MQTT cases.
